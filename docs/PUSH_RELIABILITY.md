# Доставка уведомлений PWA

## Исправленные причины пропусков (0.13.35)

- Отправка заявки обращалась к `PushDelivery.event`, которого нет в модели. Исключение оставляло запись в PROCESSING и прерывало оставшиеся очереди в текущем цикле.
- У общих чатов, комментариев и пусконаладки не было браузерной очереди: их обрабатывал Android-канал. Теперь используется существующая таблица PlanningPushDelivery; миграций нет.
- Очередь отпусков выбирала только подписки первой организации браузера. Подписка теперь используется по владельцу с повторной проверкой доступа в организации события.
- Пуш, полученный браузером, терялся при временной недоступности дополнительного API или локальной базы курсоров. При сетевом сбое показывается нейтральный текст; 401/403 (включая истёкший cookie-сеанс) оставляют только нейтральный текст без данных заявки; 404 и устаревший статус подавляют показ. Право получателя проверяется отправителем перед передачей push-провайдеру.
- Курсор считался обработанным до showNotification. Теперь он сохраняется только после успешного показа, одновременно пришедшие повторы сериализованы.
- Подписка сверялась с сервером только при заходе в настройки. Теперь она восстанавливается при открытии, возврате фокуса, появлении сети, смене worker и ротации подписки. Явное выключение сохраняется.
- Слишком большой WebPush payload мог получить 413. Конверт ограничен 3000 UTF-8 байт; полная запись остаётся в защищённом приложении.

## Семантика и повторы

SENT означает принятие WebPush-провайдером, а DISPLAYED — успешный showNotification, подтверждённый подписанным одноцелевым квитком. Это не принятие заявки, не прочтение сообщения и не подтверждение человеком.

Сбой одной записи или канала не блокирует остальные. У временных ошибок до 8 попыток с паузой до 10 минут. Без квитка показа принятый провайдером WebPush повторяется не более трёх отправок; браузер удаляет дубли. Lease восстанавливает записи после рестарта worker; завершение записи проверяет номер попытки и PROCESSING, чтобы не перезаписать квиток или чужую новую попытку. 404/410 удаляют истёкшую подписку.

Для заявок и личных заданий сохраняется ограничение актуальности 30 минут и проверка текущего статуса. TTL теперь соответствует оставшемуся окну, а не пяти минутам. Общие непрочитанные события хранятся у push-провайдера до суток. Прочтение, отозванный доступ, фильтры «только мои», тихие часы и категория уведомления могут намеренно подавить пуш. История приложения от этого не удаляется. Один tag заявки представляет актуальное состояние, а не все прежние этапы.

## Проверка на реальном сервере

1. После установки переоткрыть PWA, открыть «Настройки → Уведомления».
2. Нажать «Проверить доставку с сервера». Проверка идёт только на текущее устройство: API → PostgreSQL очередь → worker → WebPush → service worker → showNotification → подписанный квиток.
3. Повторить, свернув PWA; проверить реальную заявку и сообщение чата. Сохранить время и категорию события, если подтверждения нет.
4. Получить безопасную сводку в обоих контейнерах:

```bash
sudo docker exec liftcontrol-api-1 python manage.py push_diagnostics
sudo docker exec liftcontrol-push-worker-1 python manage.py push_diagnostics
```

Если имена отличаются, их можно увидеть через `sudo docker ps --format '{{.Names}}'`.

Сводка содержит только числа, времена и признаки конфигурации. В API отсутствие приватного ключа нормально; в push-worker ожидаются private_key_readable=true и vapid_pair_matches=true. Содержимое сообщений, endpoints, auth и VAPID-ключи в отчёт не включаются. Тексты исключений worker также не печатаются — только тип и этап.

Доставка на конкретный телефон зависит также от push-провайдера, доступности сети, разрешения уведомлений и ограничений фоновой работы ОС. Локальные тесты и GitHub CI не подтверждают настройку VAPID и доступность provider на пользовательском VPS; для этого нужна серверная проверка и её квиток.
