# Подпись APK LiftControl: один закрытый ключ, любые инструменты разработки

**Не коммитить `.jks`, `.keystore`, Base64 ключа, пароли, файлы `key.properties` или токены.** Закрытый ключ даёт право выпустить обновление от имени приложения. Приватный репозиторий не равнозначен хранилищу секретов: доступ к истории Git/веткам и CI могут получить новые участники.

## Почему прежний CI не смог подписать

В GitHub Actions при сборке PR #13 появился `SIGNING_KEY_MISSING`. В исходном workflow использовался `actions/cache` с файлом `~/.android/debug.keystore`. Кэш GitHub привязан к веткам и может быть удалён, поэтому он не подходит для постоянного хранения ключа. Ранее подписанный APK 0.6.0 beta build 2061 существует, но сам APK **не содержит закрытого ключа**, из него ключ восстановить нельзя.

**Требуется восстановить ровно тот же исходный keystore**, сертификат которого имеет SHA-256:
`7692c3fedf4b66ac2673a29326c8fb7fbc73db91af1dcee889dacbe008e32683`.

## Подписанная beta 0.13.0 от 18 ноября 2026 года

Прежний кэш `liftcontrol-private-beta-signing-v1` в ветке `feature/android-client` сохранился. После открытия репозитория подписанная сборка [44251599326](https://github.com/sergeyviktorovich87/LiftControl/actions/runs/44251599326) восстановила ключ только внутри одноразового runner и проверила сертификат до сборки и после подписи APK. Закрытый ключ не включался в логи, Git или артефакты. Файлы ключа удалены с runner после сборки.

Для этого выпуска использован [отдельный workflow](https://github.com/sergeyviktorovich87/LiftControl/blob/feature/android-client/.github/workflows/android-sign-preserved-v013.yml) исходной ветки: только она видит свой старый кэш. Исходники приложения закреплены на `d3f244801e29d7a95370e2bcb14eaac363ebc6a7`, действия GitHub закреплены по SHA. Это разовое восстановление beta, а не замена защищённой схемы ниже.

[Скачать подписанный APK и комплект проверки](https://github.com/sergeyviktorovich87/LiftControl/releases/tag/android-v0.13.0-beta.1.1): Android `0.13.0`, пакет `ru.liftcontrol.app.beta`, фактический `versionCode=5111` (у прежней beta — `2061`), SHA-256 APK `cac11dfd0203e5fabb5969646a6611365aa4daed6ddae8badfdfcd467bb2685b`. Сертификат совпадает с опубликованным APK 0.6.0 beta. Устанавливать поверх существующей beta, не удаляя её. Установка и сохранность конкретной очереди на Samsung/Honor проверяются владельцем на телефоне.

Постоянная копия ключа в `android-signing` этим выпуском **не настроена**. Кэш не является надёжным или защищённым хранилищем, особенно у публичного репозитория. Для дальнейшего использования beta владелец переносит прежний ключ в защищённые секреты и делает зашифрованные резервные копии по порядку ниже. Для коммерческого production по-прежнему нужен отдельный постоянный ключ.

Если ключ был сохранён только в Actions Cache исходной ветки `feature/android-client`, необходимо извлечь и **зашифровать** резервную копию через доверенный процесс с публичным ключом владельца. Нельзя печатать содержимое keystore/Base64 в логах или загружать его как обычный артефакт. Если исходный закрытый ключ действительно утрачен, новый ключ **не сможет** подписать обновление поверх установленной APK с прежней подписью. Нужна отдельная контролируемая миграция с предупреждением о переустановке и риске потери локальной офлайн-очереди.

## Однократная настройка владельцем

1. В GitHub откройте **Settings → Environments → New environment**, имя **`android-signing`**.
2. Настройте защиту среды: разрешайте запуск **только для `main`**, назначьте владельца обязательным проверяющим (если защита доступна для тарифа и приватного репозитория). Ограничьте, кто может писать в `main` и менять workflows.
3. Добавьте в **Environment secrets**, не в текстовые файлы Git:
   - `LIFTCONTROL_ANDROID_KEYSTORE_BASE64`: Base64 содержимого **исходного** keystore.
   - `LIFTCONTROL_ANDROID_KEYSTORE_PASSWORD`: пароль keystore.
   - `LIFTCONTROL_ANDROID_KEY_ALIAS`: alias нужного ключа (старые beta часто используют `androiddebugkey`, но не угадывайте).
   - `LIFTCONTROL_ANDROID_KEY_PASSWORD`: пароль записи ключа.
4. Перед передачей секретов в GitHub проверьте отпечаток сертификата на своей машине:
   ```bash
   keytool -exportcert -keystore /private/path/original.keystore -alias androiddebugkey | openssl dgst -sha256
   ```
   В примере alias заменяется настоящим. Команда запрашивает пароль локально.
5. Храните **две зашифрованные резервные копии keystore** за пределами GitHub, с отдельным хранением паролей и проверкой восстановления. Не присылайте keystore и пароли в ChatGPT.

## Сборка независимо от используемой модели

Разработчики и любые модели вносят изменения в отдельных ветках и открывают PR. Обычный `.github/workflows/android.yml` запускает тесты, но **не получает ключ** и создаёт лишь CI-debug APK, который **не является обновлением**.

После проверки и включения кода в `main`: откройте **Actions → Sign LiftControl Android beta release → Run workflow** и выберите `main`. Защищённая среда выдаст ключ только доверенному job. Сборка строго проверит пакет `ru.liftcontrol.app.beta`, отпечаток прежнего сертификата и versionCode выше уже выпущенной сборки 5111. Начальная база защищённой сборки поднята до 3200; с поправкой ARM64 следующий APK получает не меньше 5201. Результат будет в **Artifacts**, с `android-release.json` и контрольной суммой. Подписанный APK сначала проверяется на тестовом телефоне и только после этого публикуется в `/opt/liftcontrol/updates/android/` по проверенной инструкции.

Публикация на рабочем сервере **не производится автоматически**. Для будущего коммерческого приложения потребуется отдельный постоянный production-ключ, не смешанный с beta. Если функция не проверена, signed workflow не запускать.

## Что проверить перед раздачей beta 0.13.0

- Сервер и веб-панель используют одинаковую новую логику дежурств.
- Android 0.13.0 beta собран из того же одобренного коммита, что и API; сохранены `X-Organization-ID` и история.
- Переустановка приложения не требуется: APK накатывается поверх старой с **тем же сертификатом**, новым versionCode.
- На сервере создана и проверена резервная копия; тест без сети не удаляет несинхронизированные данные.
- Для дежурств: повторный график на тот же месяц, замена одного будущего дежурного, запрет изменения текущей смены и сохранение запроса подмены.

Это обеспечивает независимость подписи от ChatGPT, Codex, Sol и любого другого инструмента: ключом владеет только защищённый GitHub Actions, а не модель.
