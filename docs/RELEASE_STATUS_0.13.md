Дата: 14.11.2026. Ветка: `feature/release-v013`. Черновой [PR #17](https://github.com/sergeyviktorovich87/LiftControl/pull/17).
**Статус: код в GitHub, НЕ опубликовано на VPS, подписанная APK НЕ собрана, приёмка НЕ пройдена.**

## Что закоммичено (проверка кода ещё обязательна)

- Исходники: merge актуальной `feature/release-v012` и всех изменений PR #16 без удаления истории.
- Единая версия **0.13.0**: Django / React / Flutter. Android `version: 0.13.0+3100` как исходный ориентир; защищённый release workflow собирает с номером `3100 + run_number`. Нужен старый ключ подписи с отпечатком, проверяемым CI; секреты НЕ в Git.
- Сохранились предыдущие работы: повторный график дежурств, запчасти с фотографиями, связанные сообщения чата, FCM и дополнительный собственный HTTPS Push, серверный каталог обновлений APK, отдельный FCM Push о новой APK и версия фактической установленной программы в меню.
- API и модели модуля **«Пусконаладка»**: объекты, лифты, исполнители, прогресс с журналом и ревизиями, запросы добавления лифта, потребности/блокировки, допработы/решения, расходы и фото чеков, переписка объекта и архивирование.
- Ограниченная роль `ADJUSTER`: вход без карточки штатного механика, запрет обычных заявок, заданий, общего чата, медиатеки и сотрудников прямым API. Общий объект виден назначенным, проценты изменяются только по своему лифту, руководитель процент не меняет; приватные расходы видны только автору и руководителю.
- Веб-интерфейс и **Android**: экран объектов наладки, назначений, прогресса, истории, расходов, допработ, потребностей и чата. Android поддерживает фото чека из камеры/галереи. Все действия по наладке сейчас требуют связи и серверной проверки полномочий.
- Печатный **PDF-журнал ТО**: серверная выдача с проверкой организации, A4 альбомная, 6 колонок, кириллица, повтор заголовка, подписи остаются пустыми. Ссылки в вебе и Android. Это пока рабочий образец; официальный шаблон необходимо сверить с Excel заказчика и требованиями РФ.
- **Центр уведомлений**: постоянная серверная лента с отдельным состоянием прочтения по пользователю и организации. Уведомления формируются при событиях обычных заявок, личных заданий, общего чата и сообщений объекта наладки. В меню Android и вебе доступны «Все/Новые» и переход к соответствующему разделу. Прочтение НЕ равно «Принял заявку». Android системный push продолжает работать отдельно.

## Подготовленные проверки

- `backend/core/tests_commissioning.py`: два наладчика / два лифта, приватные чеки, ревизии, прямой API, согласования, архив.
- `backend/core/tests_maintenance_pdf.py`: PDF заголовок, кэш, доступ между организациями, проверка диапазона дат.
- `backend/core/tests_notification_inbox.py`: пользовательская лента, запрет отметки чужого сообщения, приватность по организации и ограниченный доступ наладчика.

## Не считать реализованным / блокеры

- **CI не выполняется**: GitHub Actions мгновенно завершается до первого шага и не получает runner. Пример: [Django run #43519903407](https://github.com/sergeyviktorovich87/LiftControl/actions/runs/43519903407), `runner_id=0`, `steps=[]`. Поэтому миграции, Python tests, web build, flutter analyze/test, Android emulator НЕ прошли подтверждённую проверку. Это не зелёный статус и не доказанная ошибка исходников.
- Полный зашифрованный офлайн-outbox для **нового** модуля наладки/чеков/чата не готов. Обязателен до использования на объектах без сети; старый offline-outbox для заявок не подменяет эту задачу.
- Собственный HTTPS Push пока не гарантирует **фоновую** доставку без Google; на Honor/Huawei требуется проверка сна экрана/Doze. FCM остаётся основным каналом.
- Центр уведомлений пока не имеет полного набора фильтров, адресной настройки и подтверждений доставки/прочтения сообщений. Переход к личному заданию в Web открывает раздел, а не всегда точную карточку.
- Нет полноценного общего чата **всех** наладчиков с защищёнными вложениями внутри новой подсистемы; есть чат объекта (текст) и прежний общий чат для сотрудников.
- Права по модулям внутри карточки сотрудника, отзыв полномочий с перераспределением лифтов и поддержка нескольких ролей внутри одной организации требуют доработки.
- Шаблон PDF надо сверить с **«Журнал ТО Мегаполис.xlsx»**; официальная юридическая форма пока не утверждена.
- Не реализованы заявленные варианты цветов для Android и Web; текущая цветовая схема сохранена.
- Не выполнены полноценные полевые и нагрузочные тесты, миграции на PostgreSQL 18, восстановления из бэкапа, установки APK поверх старой и связи с FCM.
- **Android APK 0.13.0 для установки отсутствует**: защищённая сборка запускается только от проверенного main после CI и доступа к сохранённому сертификату. Debug APK не должен устанавливаться поверх рабочего приложения.

- Репозиторий `LiftControl` и черновой PR #17 сохранены; права владельца на repository подтверждены.
- Повторно запущены Actions Django и Android. GitHub принял повторный запуск, но **оба завершились до первого шага** (`runner_id=0`, `steps=[]`). После оптимизации CI на новом коммите [Django #43527637941](https://github.com/sergeyviktorovich87/LiftControl/actions/runs/43527637941) и [Android #43527637813](https://github.com/sergeyviktorovich87/LiftControl/actions/runs/43527637813) повторяют ту же проблему.
- Вероятный внешний блокер: бюджет/списание GitHub Actions для **частного** репозитория, ограничение раннеров или удержание аккаунта. Это **не подтверждено диагностикой Billing**, потому что доступ к настройкам оплаты аккаунта в текущем подключении отсутствует. Официальные материалы: https://docs.github.com/en/actions/how-tos/troubleshoot-workflows и https://docs.github.com/en/billing/how-tos/troubleshooting/locked-account.
- Владелец проверяет **GitHub → Settings → Billing and licensing → Budgets and alerts / Usage → Actions**, лимит $0, доступные включённые минуты, предупреждения об оплате и блокировки. Изменение платёжного лимита только с его согласия. При отсутствии признаков проблем с оплатой: запрос в GitHub Support со ссылкой на один из провалившихся workflow.
- Сокращено число автоматических запусков: полный Django и Android тестируется при изменении PR и на main, Docker-образ автоматически собирается для main либо вручную, старые параллельные запуски отменяются.

- История уведомлений больше не раскрывает старые данные после смены роли или снятия назначения с объекта; добавлены тесты приватности. Уведомления о собственных сообщениях исключаются.
- Фото чеков: защищено от параллельной замены, повторной загрузки и слишком больших изображений; добавлен тест неизменяемости чека.
- Проведена статическая проверка строк версий Django, Web, Flutter, workflow подписи и зависимостей миграций: **10/10 совпадают с 0.13.0**. Это не означает успешную компиляцию.

## Публичное зеркало CI (подготовлено, ещё НЕ опубликовано)

После исчерпания бесплатных минут в приватном репозитории выбран отдельный публичный `LiftControl-CI` без переносимой истории и без доступа к рабочему серверу. Инструменты: `tools/public_ci_snapshot.py`, строго ограниченный перечень `tools/public_ci_allowlist.json` (**174 проверяемых путей исходников**), регрессионные проверки `tools/tests/test_public_ci_snapshot.py`. Процедура описана в [PUBLIC_CI_MIRROR.md](PUBLIC_CI_MIRROR.md).

Исключены реальные данные импорта объектов и сотрудников; демонстрационные названия и адреса заменяются на фиктивные. Защитный экспорт отменяется при появлении неизвестного файла, потенциального секрета или постороннего IP. Само наличие экспортёра не означает, что вся кодовая база уже прошла независимый security review.

**Блокер:** GitHub connector не имеет операции создания репозитория. Владелец должен создать пустой **Public** `sergeyviktorovich87/LiftControl-CI` (https://github.com/new) и предоставить ему доступ через подключённый GitHub. После создания нужно перенести только очищенные файлы, запустить CI и проверить результат. Исходный `LiftControl` не переводить в public.
