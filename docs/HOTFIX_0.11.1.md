# Хотфикс LiftControl 0.11.1 / Android 0.6.1 beta

**Статус: в разработке, не развернут.** [PR #14](https://github.com/sergeyviktorovich87/LiftControl/pull/14) основан на [подготовке репозитория #13](https://github.com/sergeyviktorovich87/LiftControl/pull/13). Исправление не является частью планируемого собственного Push-сервиса 0.12.

## Причина

Android 0.11/0.6.0 всегда отправляет `replace:false` в `duty/preview/`. При повторном составлении уже занятого графика API корректно пропускает все даты. Пользователь ошибочно воспринимает это как невозможность повторного редактирования. Веб-панель ранее имела опцию замены, но не запрашивала отдельное подтверждение перед массовой операцией.

## Исправлено в ветке (не на рабочем сервере)

- Android: переключатель «Заменить существующий график», количество замен в предпросмотре, подтверждение перед применением; самостоятельная смена будущего исполнителя.
- Django: журнал изменения будущей смены, запрет удаления смены с историей подмены и запрет тихой правки смены с ожидающим запросом подмены. Состоявшиеся и начавшиеся дежурства нельзя переписать.
- Web: дополнительное подтверждение массовой замены существующих смен.
- Регрессионные тесты: повторное редактирование, отдельная смена, права и чужая организация, сохранение запросов подмены.
- CI: проверки Android без подписи. Выпускная APK только через отдельный защищённый workflow, с прежним сертификатом.

## Проверить до объединения

- [ ] Django и тесты расписаний зелёные на PostgreSQL.
- [ ] Flutter analyze/test и Android-эмулятор прошли; Web собран и проверен.
- [ ] Изменить график на следующий месяц, затем повторно составить для **тех же дней**, сначала без замены (ничего не затереть), затем с заменой; проверить точные даты, количество смен и журнал.
- [ ] Изменить одного будущего дежурного дважды, проверить оба клиента и историю.
- [ ] Нельзя изменить начавшуюся смену; подмены с историей не стираются; другой работодатель не видит чужое расписание.
- [ ] Восстановить прежний Android keystore и настроить защищённую среду согласно [ANDROID_SIGNING.md](ANDROID_SIGNING.md).
- [ ] После проверки и переноса в `main` запустить **Sign LiftControl Android beta release**. Проверить `ru.liftcontrol.app.beta`, прежний сертификат, versionCode больше 2061, SHA-256 и наличие `android-release.json`.
- [ ] На резервной копии VPS проверить миграции и обновление. Затем, с резервной копией данных, обновить API/Web и опубликовать APK через установленный механизм обновлений.
- [ ] Установить APK **поверх** установленной версии на Android и проверить, что локальная очередь и авторизация не потерялись. Не удалять старое приложение ради перехода.

## Требуется от владельца

1. Сейчас: предоставить безопасное подтверждение наличия прежнего keystore **без передачи его или пароля в чат**, настроить GitHub Environment и проверить права ветки `main`.
2. Перед публикацией: протестировать исправление графика в вебе и на телефоне на двух будущих датах и двух сотрудниках; проверить свежую резервную копию БД и медиа.
3. После теста: разрешить публикацию хотфикса. При невозможности восстановить старый ключ останавливаем OTA-обновление до отдельного плана миграции, не создаём новый ключ самовольно.
