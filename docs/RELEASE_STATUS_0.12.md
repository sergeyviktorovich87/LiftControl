# LiftControl 0.12.0: состояние разработки

Обновлено: 13.11.2026. **Статус: рабочая ветка, не опубликовано, не принято.**
Исходники: [PR #15](https://github.com/sergeyviktorovich87/LiftControl/pull/15) от исправленной базы [PR #14](https://github.com/sergeyviktorovich87/LiftControl/pull/14). PR #13 должен быть безопасно завершён перед включением 0.12 в основную ветку.

## Уже изменено в исходном коде

- Django API `core/updates.py`: `VERSION = '0.12.0'`.
- Health API `core/views.py`: `version: 0.12.0`.
- React `web/package.json`, `package-lock.json`, интерфейс: `0.12.0`.
- Flutter `mobile/pubspec.yaml`: `0.12.0+1200`. Подписывающий workflow задаёт больший `versionCode` с учётом номера запуска. Важно, чтобы итоговый код превышал код установленного APK 2061, **самого файла APK из этого не следует**.
- Собственный HTTPS-канал Push из [PR #12](https://github.com/sergeyviktorovich87/LiftControl/pull/12), рядом с FCM: события по организации, исключение повторов, диагностический статус. **Это лишь опрос активного приложения, не гарантия фоновой доставки**.
- Планировщик из PR #14: повторная замена будущих графиков, редактирование будущей смены, подтверждения и журнал действий. Не меняет уже начавшиеся смены.
- Фотографии к заказам запчастей с проверкой организации, ограничениями размера, защищённым скачиванием и мягким удалением; при изменении согласованного заказа снова требуется согласование.
- Изменение заявки на запчасть в API, Web и Android с аудитом; заказанные и полученные позиции нельзя переписывать без отдельной процедуры.
- Связанные карточки заявки/запчасти в общем чате, отправка ссылок из Web и Android, открытие исходника, запрет чужой организации. Работа офлайн с карточкой идёт через существующий Android outbox.

- Пока CI не завершился успешно, пункты выше означают **код в ветке**, а не «готово к установке».

## Что ещё не внедрено (важные требования)

Полный центр истории уведомлений, приём заявки прямо из шторки Android, надёжный альтернативный Push в фоне, файловый кэш для скачанного, права внешних наладчиков, многоорганизационные назначения и увольнение с передачей лифтов, статус «Длительный ремонт», PDF-журнал ТО, полная «Пусконаладка», расширенные темы и остаточные пункты [плана 0.12](RELEASE_PLAN_0.12.md) и [плана 0.13](RELEASE_PLAN_0.13.md).

Не перемещать эти задачи в «готово» на основании одного макета или успешной сборки Flutter.

## Ограничения выпуска и подписи

Подписанная APK 0.12.0 **не собрана**. Старый beta keystore отсутствует в доступном CI-контексте; заменить ключ новым нельзя без переустановки установленного приложения. Режим подписи через GitHub Environments подготовлен, но требует сохранённого первоначального ключа и пользовательской настройки защищённой среды, см. [ANDROID_SIGNING.md](ANDROID_SIGNING.md).

Не публиковать APK и не обновлять рабочий VPS до:
1. полного зелёного CI;
2. проверки прежней Android-подписи и versionCode > 2061;
3. резервной копии PostgreSQL и медиа с проверкой восстановления;
4. ручной приёмки функций на двух ролях и в двух организациях;
5. проверки обновления APK **поверх установленной 0.11**, без потери офлайн-очереди.

## Для владельца

Потребуется восстановить **оригинальный keystore** и создать GitHub Environment `android-signing` с четырьмя Secrets, не посылая закрытые данные в чат. После подписания тестировать Web/Android и дать разрешение на выкат; до этого от владельца действий по исходникам не требуется.
