# LiftControl 0.5 — заявки, роли, история и готовность Web Push

## Внешний вид
Полностью сохранены `web/src/styles.css`, панель 0.4, меню, темы и структура интерфейса.
Добавлены действия внутри **существующих диалоговых окон**.

## Новая логика
- Диспетчер, директор, администратор, либо механик с активной сменой в графике создают заявку.
- Всем авторизованным механикам доступны заявки и история в карточках лифта.
- Принять новую заявку может закреплённый за лифтом механик; диспетчер может заранее назначить замену с причиной.
- Принятие защищено транзакцией и блокировкой строки PostgreSQL.
- Выполнивший заявку механик вводит результат ремонта, может загрузить до 8 фото и добавить комментарии.
- Только дежурный механик, диспетчер или руководитель отменяют новую/рабочую заявку с обязательной причиной (от 5 символов).
- Готовую заявку может отменить только директор/администратор, тоже с причиной.
- Физическое удаление заявок, фото, комментариев отключено в публичном API; системная история сохраняется.
- Защита разрешений применяется на Django API, а не только на кнопках React.
- Список заявок в открытом интерфейсе обновляется раз в 6 секунд, закрытый модальный просмотр — раз в 10 секунд.
- Подготовлены endpoint подписки, Service Worker, долговременная очередь и фоновая команда рассылки. **Доставка Web Push НЕ активна, пока администратор не настроит HTTPS и VAPID.**

## Что требуется от пользователя для обновления VPS
1. Скачайте приватный архив `LiftControl-v0.5-amd64` из успешного GitHub Actions run на коммите версии 0.5.
2. Распакуйте в `/home/liftadmin/update-v05/`.
3. Проверка SHA256 выполняется автоматически перед установкой; из распакованной папки запуск:
   `sudo bash /home/liftadmin/update-v05/update-v05.sh`.
4. Установщик сохраняет текущий образ API, делает резервную копию БД и уже загруженных фото/PDF, мигрирует схему, проверяет health, оставляет API на 127.0.0.1:18080.
5. Старые пользователи и связанные записи не удаляются. Создание тестовой заявки доступно под superuser; для механика назначьте Membership + соответствующий Technician и график DutyShift.

Не используйте `docker compose down -v`. После успешного обновления добавляйте `-f compose.v05.yaml` к обычной последовательности Compose (с учётом v04).

## Для запуска Web Push отдельным этапом
Потребуются HTTPS-сертификат и домен, VAPID P-256 ключи, защищённое размещение приватного ключа (root:10001 mode 0640) и небольшой фоновый процесс `python manage.py run_push_worker --interval 5` с доступом к БД и egress только к разрешённым push-провайдерам.
Контейнер API требует переменные `WEBPUSH_VAPID_PRIVATE_KEY_FILE`, `WEBPUSH_VAPID_PUBLIC_KEY`, `WEBPUSH_VAPID_SUBJECT`; секрет нельзя сохранять в GitHub или передавать через браузер. Свои HTTP-запросы не отправляют push наружу: уведомления кладутся в очереди и обрабатываются worker.
Подписка браузера требует явного действия пользователя. Не отправляйте push-подписки и журналы с их endpoint публично.
Установочный архив 0.5 **не включает автоматическое включение Web Push**: без постоянного HTTPS включать уведомления для реальных сотрудников преждевременно.

## Безопасность и известные ограничения
- Обычным механикам физическое удаление недоступно. Проверяйте права API серверными тестами.
- История событий и комментарии append-only на уровне API. Django superuser и прямой доступ к PostgreSQL технически имеют возможность изменять базу; до коммерческого запуска нужен дополнительный аудит и контролируемые восстановление/доступ.
- Push не заменяет телефонный/диспетчерский резерв для аварийных ситуаций.
- Нужны автоматические внешние резервные копии БД и media, конфигурация HTTPS, проверка прав в работе с реальными пользователями.
